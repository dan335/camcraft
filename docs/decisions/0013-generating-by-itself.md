# 0013 — Generating by itself, at once, and stopped from what changed

**Status:** decided, 2026-11-03 · **Milestone:** 0.3

## Question

A setup was generated only when Generate was pressed, one operation after
another, and a run could not be stopped: a run superseded by another was
dropped when it answered, but worked on until it did. On a large curved part
(a serving tray: 442 × 249 × 44 mm, 440 000 triangles) roughing took two
minutes to work out and the scallop after it twenty seconds, one waiting for
the other, so every change was a wait and a press. Fusion generates as you
change a toolpath and shows it as it goes. What should camcraft do, and how,
without ever making a toolpath that differs from one made the old way?

## What was decided

**A setup is generated by itself as soon as editing it settles.** Settled is
the job unchanged for 300 ms, or for 1.5 s while a field is still focused or
dragged, so a value typed and left in its field is still generated, and a
keystroke never starts a run. Every open job's setups are generated at once.
It can be turned off in Settings, where a setup is generated only when asked.

**What still stands is kept.** A run keeps every operation made before and
unchanged since, up to the first that is not, and works out that one and every
one after it: each cuts what the ones before it left (the rest machining the
run is built on), so nothing after a changed operation stands. A kept
operation is cut into the material again, as `Plan::Keep` always was.

**A run is stopped from what changed.** Each frame, a run in flight is compared
with what it was sent from: from the first operation that would now cut
otherwise, every operation is stopped; the ones before it go on, and are kept.
A change to what shapes every cut (the part, stock, tolerance) stops the whole
run. So editing the finish while the roughing is being worked out never throws
the roughing away. The run is stopped, not abandoned: a stopped operation's
work ends at the next point it asks, and the threads are free again.

**Stopping is a handle, asked at the work's own pace.** Whoever starts a run
holds a `Control`; each operation's work is given a `Watch` on it, carried in
its strategy's parameters, and asks it between passes, levels, lines, curves
or rows, whatever its loop is. A default `Watch` watches nothing, so a strategy
run on its own (by the tests, or the command line) behaves exactly as before.
The same handle says how far each operation has got, which the strategies tell
it in the same places: additively for work done at once in pieces (adaptive's
levels, scallop's rows and nodes), as a high-water mark for work done in order
(the linker's passes).

**Operations are worked out at once.** Working out an operation's passes reads
the part alone, but for pocket clearing, which clears what the operations
before it left (`Uses::rest`). So every other operation's passes are worked out
from the start, each on a thread of its own, and pocket clearing in its turn;
then each is linked over the material and cut into it in order, as before. The
result is the same however the threads go, since what each thread makes reads
nothing another writes. On the tray, the scallop's passes are ready long before
the roughing is cut.

**What is made shows as it is made.** The run tells each operation as it is
made, with the material after it; the app draws what the run has made so far
at once, its playhead where it was, and says in the tree and the operation's
panel what each operation is doing and how far it has got. A result told part
way is never finished, so never passes the gate to be posted.

**One core is left for the window.** The global pool takes every core but one,
so the window keeps drawing however long generating takes.

## What was not done

- Running the operations after a stopped one at once with what is still
  being made before it, when it could be: the run waits for what is before it
  to finish, then starts again from the changed one. Simple, and nothing is
  worked out twice.
- Finer progress than each strategy's own loop: adaptive says how far it has
  got level by level, so on a part with few levels it moves in steps.
- Working out one adaptive level on more than one core. Its levels are worked
  out at once, but the slowest is left alone at the end: on the tray, at a
  tenth of the tool's width, two of twenty cores were busy for the last few
  minutes, and the same run took twice as long when that level fell to one of
  the processor's efficiency cores. Splitting a level's clearing is next.
- Keeping results between sessions: they are worked out again on opening.
